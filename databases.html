Artifact Overview

The artifact I selected is the Travlr Getaways full-stack web application that I originally created during CS 465. The original application stored users and trips in MongoDB, but it did not include a way to connect a user to a trip through an actual reservation record.

For the database enhancement, I added a reservation system that connects authenticated users with existing trips while storing reservation-specific information such as the number of guests, reservation status, and creation date.

Reservation Data Model

I created a new Mongoose reservation schema rather than adding reservation information directly to the existing user or trip documents. Each reservation stores references to both the user and the selected trip using MongoDB ObjectIds.

This design avoids unnecessarily duplicating user and trip information inside every reservation. The reservation document stores only the information that belongs to the reservation, while related user and trip information can be retrieved when needed.

User Relationship

The user field stores an ObjectId reference to the authenticated user who created the reservation.

Trip Relationship

The trip field stores an ObjectId reference to the existing trip document selected by the user.

Reservation Data

Each reservation also stores the guest count, reservation status, creation timestamp, and update timestamp.

Validation and Data Integrity

Database-level validation was added to prevent invalid reservation records from being stored. The guestCount field is required and must contain a value of at least one.

The reservation status is also restricted to approved values: pending, confirmed, or cancelled. New reservations begin with a default status of pending.

Validation in the database model is important because client-side validation can be bypassed. Even if an invalid request is sent directly to the API, the model still protects the stored data.

Indexing and Query Design

I added indexes to fields that are commonly used when retrieving reservation information. The user and trip references are indexed, along with compound indexes supporting lookups by user and creation date and by trip and reservation status.

These indexes improve the database design by supporting the queries the application is most likely to perform. For example, the application retrieves reservations belonging to the currently authenticated user and sorts them with the newest reservations first.

API and Database Integration

I created REST API endpoints that allow an authenticated user to create a reservation and retrieve their existing reservations.

When a reservation is created, the API first finds the selected trip by its trip code. It then stores the trip's MongoDB ObjectId together with the ObjectId from the authenticated user's JWT.

When reservation information is returned, Mongoose populate() is used to retrieve useful information from the related trip and user documents without duplicating that information in the reservation collection.

Authentication and Security

Reservation routes require a valid JWT. The user identifier used for creating and retrieving reservations comes from the verified token rather than from a user ID supplied by the browser.

When a user requests their reservations, the API queries the database using the authenticated user's ObjectId. This prevents the client from simply supplying another user's identifier and requesting that person's reservation data.

Angular Integration

The Angular application was updated so logged-in users can create reservations directly from the trip cards. The user selects the number of guests, and the application sends the trip code and guest count to the reservation API.

I also added a My Reservations page that retrieves the logged-in user's reservation records and displays the trip name, resort, start date, guest count, price per person, reservation status, and the date the reservation was created.

Testing and Validation

I tested reservation creation directly through the API and through the Angular interface. I confirmed that reservations were stored in MongoDB with the correct user and trip ObjectId relationships and that related trip information was returned correctly through populate().

I also verified the stored documents directly in MongoDB Compass and confirmed that reservations were returned in newest-first order.

To test database validation independently of the user interface, I deliberately sent a reservation request with a guest count of -1 directly to the API. Mongoose rejected the request with an HTTP 400 Bad Request response because the value violated the schema's minimum requirement. No invalid reservation was added to the database.

Course Outcome Alignment

This enhancement demonstrates progress toward Course Outcomes 3, 4, and 5. The reservation system required decisions about data relationships, validation, indexing, query design, and how information should move between the database, API, and Angular application.

The enhancement also demonstrates a security mindset because reservation records are accessed through authenticated API requests and database queries are tied to the identity contained in the verified JWT.

Reflection

One of the main things I learned from this enhancement was how strongly database design affects the rest of a full-stack application. Adding reservations required coordinated changes to the database model, API controller, routes, Angular service, route protection, and user interface.

Testing the validation directly through the API also reinforced the importance of protecting data at the model level instead of depending only on controls in the browser.
